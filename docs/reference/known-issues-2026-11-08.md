## Known issues (not yet carded)
- **The client minimap shows no objective icons: fixed by card 070.** The host sends the objective's actor names (`ChanOp::ObjectiveActors`, before the objective frame, journaled; snapshot reads `USTLevelObjective+0x88`) and the client passes the resolved actors to the replay. Cause found by card 068: The card 049 replay calls `AddObjective` / `AddSubObjective` with no actors, so `ASTLevelObjectiveMarker::CreateASTLevelObjectiveMarker` (the caller at exe+0x5150FB0) never runs on the client. With no marker actor there is no `ObjectiveUpdated`, `ShowOnMinimap` or `AddNewMarker`. The rest of the chain works on the client: a marker made by the client's own level script reaches the minimap in one frame, and pickup and teammate icons draw in the right places. `MinimapRange` reads -1 on both sides. Fix: card 070 (drafted): pass the objective actors through the card 049 journal, or create the markers on the client's copy of each placed actor.
- **Shooting-range targets: fixed by card 065.** The pop is `Activate(1)` on the target's `ADLevelTriggerReactions` component, called from `LR_ActivateGeneric_C` on the host only. The host relays it as `ChanOp::Activate` (owner name and component name), and the client activates its own copy. The client's kills count, and the range completes (`tools/scenarios/c65-range.txt`). The client refuses its own `GA_ShuntAbilityCharacter_C` activation with event data, which asserted at `GameplayAbilityTargetTypes.cpp:240`, so the client's pawn is not shunted. Open: the client's ammo shows 0 in reserve and it cannot reload; the tactical support range is unproven; there is no late-join journal for activated targets.
- **Client interactor target is null** (card 050): the client's own `UADInteractorComponent` +0x100 stayed null at 130 and 164 uu while it aimed at a weapon case, so the client never sends `UseName`, and its own `Interact` does nothing. The relay works through the server copy's trace, which only finds the target when the copy stands at it. Card 054 must find out why the client's trace finds nothing (check +0xF8 range, +0x108 scene component and the interactable's enabled flag on the client) before it relies on a client-side target.
- **Pickups are not replicated** (card 050: placed pickups have bReplicates 0). **Fixed by card 056:** the host sends `ChanOp::PickupGone` (placed name) after each `DisablePickup` and replays a per-map journal of 128 names on a copy's first Pong, so a rejoining client is filled too. No re-enable op (FED_C1M1 has no respawning pickups). The text below is the history. A pickup that one machine takes is still shown on the other machine. Card 055 shot ScreenShot01321 shows the case open on the client after the client's own pickup; the host's view of that case was not captured.

- **Ammo is not synced** (card 050). **Cause of the client's empty reserve found by card 069:** in FED_C1M1 the Morita reserve comes only from ammo pickups (`BP_AmmoPickup_MoritaSmall_C`, through `USTWeaponUtilityLibrary::AddAmmunitions` 0x05229F50, which calls `SetAmmoCount`). Their overlap runs on the host, so a client's pickup credits its server copy's `USTAmmunitionInventory` (pawn+0xA48, `AmmoMap` keyed by `AmmunitionType.*`, element stride 0x14), which does not replicate. `ResetInventory` runs on every pawn but gives only `AmmunitionType.Laser` 300, and it re-adds weapons. The player's reload is `USTWeaponReloadAbility::RequestNewAmmunitionFromInventory`, which calls `SetAmmoCount` directly; `PerformReload`, `DoAction` and `RequestAmmo` are not on that path. **Card 071 relays it:** the host's `AddAmmunitions` detour sends a server copy's gain per ammunition type as `ChanOp::Ammo`, and the client calls `AddAmmo` on its own inventory. Card 072 (done) seeds the client's counts from the copy once per spawn (`ChanOp::AmmoSet`), mirrors the client's counts to its copy every 250 ms (`ChanOp::AmmoMirror`), and re-applies them because the copy runs its own reload. **Grenades: fixed by card 073.** The count lives in the pawn's `ItemInventory` (`Items` +0xD8, `Quantity` +0x38); the host relays each server-copy grenade item count as an absolute `GrenadeItem` text, and the client binds its grant to the replicated spec and sets `SourceItem` to its own item. Card 073 step 0 also holds the card 072 respawn seed until the new pawn has an inventory. **Card 074 (done) shows them:** the host relays each grenade spawn (`ChanOp::GrenadeSpawn`) and explosion (`GrenadeExplode`: system, sound, damage zone), and the client plays cosmetic copies with no damage (the zone copy has collision off). Gaps: the zone copy lasts a 10 s fallback, and the host's grenade in flight is often hard to see on the client.

- **A client death turns off the host's autosave** (card 030; severity unclear). Caution (static, senior): `USTDebugSaveTracker` looks like a debug save-session recorder, not the player's checkpoint save. Its natives include `StartSession`, `EndSession`, `IsInSaveSession`, `IsInReadOnlySession`, `Export`, `Import`, `OpenFileDialog`, `LoadNextSave` and `SetSaveInterval`. Checkpoint saves appear to go through `ASTCheckPointSaveZone` (`OnBoxComponentOverlap`, `SetSaveZoneEnabled`) and `ASTSaveableLevelScriptActor`. Before building a fix, log `IsInSaveSession` and `IsAutoSaveEnabled` in a normal run, and check whether a checkpoint still saves after a client death. Details: the server copy's `StartDeath` calls `USTDebugSaveTracker::SetAutoSaveEnabled(0)`, and nothing turned it back on in the logged window (only map load calls `SetAutoSaveEnabled(1)`). Static (senior): the `(1)` call comes from `ASTPlayerController::ForceInputEnabled(bool)` (0x051C67B0). That function enables or disables input through the vtable (+0x330 / +0x340); then, if controller +0x7C0 is non-null, it calls `SetAutoSaveEnabled(b)` on `GetSTGameInstance(this)` +0x1D0, the `USTDebugSaveTracker`. So autosave follows the host controller's input state, while `StartDeath` (0x051DE410, call at +0x8D) turns it off directly, even for the client's server copy. A fix can call `SetAutoSaveEnabled(1)` (0x0521B160) on that tracker after a non-host-own `StartDeath`, or skip the call in a `SetAutoSaveEnabled` detour when its caller is `StartDeath` on a pawn that is not the host's own. The downed or death design must avoid this or restore autosave. Senior static, 2026-11-04: `Save_CheckPoint` 0x052180E0 gates on the PC's byte +0x7B8 and `CanCheckpointSave`, and does not read the tracker's autosave flag (+0x3A), so checkpoints are not expected to stop. Card 050 step 5 checks this at runtime.

- **Kill floor bypasses downed** (senior static, 2026-11-04): `ASTPlayerCharacter::Tick` 0x051E06F0 asks `USTCommonUtilityLibrary::IsBelowKillThreshold` 0x05242110 (root Z <= `USTGameInstance::GetCurrentChapterKillZ` 0x050E99E0) and, when true, sets Flying and calls `StartDeath` through vtable +0xA40, skipping `HandleDeathEvent`. It runs on every machine. Its other caller is `ASTNonPlayableCharacterBase::Tick`. Card 046 (done) detours `IsBelowKillThreshold` for player pawns: the host warps or downs, and the client always returns false for player pawns and waits for `ChanOp::Warp`; that branch first goes live in the playtest, because card 049 gave the client a real KillZ.

Switches, satchel sites, ziplines, turrets, item and weapon pickups used by the client happen in the client's world only. Card 050 Addendum 4 relays the pickup classes; the wider relay is card 054.
