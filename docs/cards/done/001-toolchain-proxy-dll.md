### Junior report — resumed and completed (2026-11-02)

**Status: done.** Everything compiles and links with `/W4 /WX`. The game was not launched. `game/`, `prefix/` and `logs/` were only read, never written. No commits.

Files created:
- `toolchain/clang-cl-xwin.cmake`: targets x86_64-pc-windows-msvc with clang-cl, lld-link, llvm-lib and llvm-rc. Headers come in through `/imsvc` (crt, ucrt, um, shared) and libraries through `/libpath`. It sets `CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY` because xwin ships no debug CRT and CMake's compiler probe would otherwise fail on `msvcrtd.lib`.
- `mod/CMakeLists.txt`: builds MinHook v1.3.4 as a static lib from the vendored sources (MinHook's own CMakeLists is not used). Target `ubwcoop` has output name `dwmapi.dll` and uses the static release CRT `/MT` for every config.
- `mod/src/dllmain.cpp`: on attach it opens the log, loads the real DLL, then starts the worker thread, which installs the hooks.
- `mod/src/log.{h,cpp}`: writes `UBWCoop.log` next to the exe (`GetModuleFileNameW(NULL)` dir; truncated on each start), guarded by an SRWLOCK, with timestamp and thread id on each line.
- `mod/src/proxy.{h,cpp}`: one naked stub per export, `jmp [ubw_real+8*idx]`. The table is filled in DllMain from `GetSystemDirectoryW()\dwmapi.dll`. Named exports are resolved by name, NONAME exports by ordinal.
- `mod/src/hooks.{h,cpp}`: checks the exe identity, checks the RVA, then installs a MinHook hook on `UGameEngine::Init` that logs `fired` and `returned`.
- `mod/src/dwmapi.def`, `mod/src/proxy_exports.generated.inc`: generated by `tools/gen_proxy_exports.py`.
- `mod/src/offsets.generated.h`: generated by `tools/pdb_rva.py gen` from `tools/symbols.txt`.
- `tools/pdb_rva.py`: subcommands `lookup NAME...` and `gen`.
- `tools/symbols.txt`: one entry, `UGameEngine_Init`.
- `tools/gen_proxy_exports.py`

Exact commands (from the repo root):
```
python3 -I tools/gen_proxy_exports.py      # 84 exports (37 named) -> dwmapi.def, proxy_exports.generated.inc
```

Proof:
- Build: `[10/10] Linking CXX shared library dwmapi.dll`, with no warnings under `/W4 /WX` (MinHook is built at default warnings, not `/WX`, since it is third-party).
- Exports: I dumped `llvm-readobj --coff-exports` (ordinal + name) for both GE-Proton11-11 `dwmapi.dll` and `build/dwmapi.dll`, and `diff` reports them **identical**: 84 entries, ordinals 100–183, 37 named and 47 NONAME. The reference file is byte-identical to `prefix/drive_c/windows/system32/dwmapi.dll`.
- Stubs: I disassembled four exports. Ordinal 100 (idx 0) is `jmpq *(0x180022bb0)`, 103 (idx 3) is `+0x18`, 165 `DwmFlush` (idx 65) is `+0x208`, and 183 (idx 83) is `+0x298`. All four land in `.data` (0x22000+). A `static_assert` ties each generated index to its ordinal.
- RVA: publics give `0001:63015632` and `.text` VA is 0x1000, so the RVA is 0x03C19AD0. Disassembly of the exe at 0x143C19AD0 shows a normal prologue (`mov [rsp+18h],rbx; mov [rsp+20h],rsi; push rbp; ...; sub rsp,240h`), which MinHook can hook. `pdb_rva.py` also resolved `UEngine::Browse` to 0x043D4840 (lookup only, not hooked). An unknown name exits 1 with "symbols not found".
- `pdb_rva.py` refuses to run unless the PDB GUID and age match the exe's CodeView record. At runtime `hooks.cpp` does the same check against the in-memory exe (GUID {CE4531D7-...-2F A3}, age 1). It also requires the RVA to fall in an executable section, and it logs FATAL and installs nothing if either check fails.

Decisions for the senior to check:
1. **dwmapi over winmm.** Both are static imports of the exe and neither is delay-loaded. dwmapi has 84 exports against 189 for winmm, so it is the smaller surface. winmm is also loaded early by many other DLLs (audio), which makes ordering riskier. The exe calls only 4 dwmapi functions.
2. **Export list mirrors Proton's dwmapi, not Windows'.** The DLL only ever runs under GE-Proton. Ordinal-only Windows exports that Wine lacks don't matter, because the game imports by name.
3. **The real DLL is loaded inside DllMain** (`LoadLibraryW` under the loader lock). Many proxies do this, but Microsoft discourages it. If loading fails, or `LoadLibraryW` returns our own module, DllMain returns FALSE so the game refuses to start, with FATAL in the log. A single export missing in the real DLL is logged as ERROR and routed to a stub that returns `E_NOTIMPL`.
4. **Hooks go in from the worker thread, not DllMain**, because MinHook suspends threads. This leaves a theoretical race: the hook could be enabled after `UGameEngine::Init` has already run. That is very unlikely, since Init happens seconds into boot, but a log with "hooked" and no "fired" would mean exactly that.
5. The static CRT avoids any vcruntime dependency inside the prefix.

Uncertainties (need a runtime test, which is senior-owned):
- **Wine same-name load.** It is unverified whether Wine's `LoadLibraryW("C:\windows\system32\dwmapi.dll")` returns the builtin rather than our already-loaded `dwmapi` module. ASI-loader-style proxies rely on this working. The self-check makes a failure obvious either way.
- Deploying is a manual step that was not done: copy `build/dwmapi.dll` next to the Shipping exe and launch with `WINEDLLOVERRIDES=dwmapi=n,b`. The expected log is `proxy: resolved 84/84`, then `hooks: UGameEngine_Init hooked`, then `UGameEngine::Init fired`.
